⏺ Before questions, here's what I verified — a few things change your plan.

  Fact-checks that matter:

  1. "LangChain" doesn't exist on the JVM. LangChain is Python/JS. On Kotlin
  your options are LangChain4j
  (https://docs.langchain4j.dev/tutorials/spring-boot-integration/) (an
  independent, LangChain-inspired framework — 1.17.2, ships a dedicated
  -spring-boot4-starter) or Spring AI 2.0
  (https://spring.io/blog/2026/06/12/spring-ai-2-0-0-GA-available-now/) (GA June
  2026, requires Boot 4 — matches your 4.1.1 parent). Learning LangChain4j will
  not transfer cleanly to LangChain/LangGraph interviews or tutorials. That's a
  real fork in the road.
  2. Your "multi-provider architecture" is mostly free already. OpenRouter
  (https://openrouter.ai/api/v1), Requesty (https://docs.requesty.ai/quickstart)
  (https://router.requesty.ai/v1), and local Ollama/LM Studio are all
  OpenAI-compatible. Swapping them is base-URL + key config, not an abstraction
  layer. Building a provider SPI on day one would be speculative generality.
  3. Free hosting is worse than you assume. Koyeb's free tier closed to new
  users (https://www.srvrlss.io/provider/koyeb/) after the Mistral acquisition;
  Fly.io dropped free for new accounts. Render's free tier survives but sleeps,
  and a JVM eats 200–300MB of a 512MB box before your code runs.
  4. Neon free: 0.5 GB/project, 100 compute-hours, scale-to-zero after 5 min
  idle (https://neon.com/blog/how-to-make-the-most-of-neons-free-plan) — your
  connection pool must survive cold starts.

  Gaps in the idea itself: there's no notion of tracking applications over time
  (you'll analyze 50 offers — where do they live?); no cover letter generation,
  which is cheaper than a CV and higher leverage; no skill taxonomy, so "React"
  in one offer and "ReactJS" in another become different gaps and your report is
  noise; and critically — nothing stops the AI from inventing experience you 
  don't have on the tailored CV.

  Let me write this down, then grill you.

⏺ Round 1

  ❓ Q1 — "I want to learn LangChain" vs. "I want a Kotlin app": These are in
  tension and you can't have both cheaply. LangChain4j shares vocabulary with
  LangChain (chains, memory, tools, retrievers) but is a different codebase with
  different APIs — you'd learn the concepts, not the framework. Spring AI 2.0
  is the better-integrated Boot 4 citizen but shares even less DNA. A Python
  sidecar running real LangChain/LangGraph gets you the actual framework, but
  you now run two processes, two deploy targets, and a network hop — which kills
  "lightweight MVP". Which do you actually want: the concepts on the JVM, the
  best Kotlin integration, or genuinely LangChain?

  ➡️ LangChain4j. You get the LangChain mental model (AiServices, tools, memory,
  structured output) inside one Kotlin process. If you later want real
  LangChain, the concepts port; the code never would anyway.

  ---
  ❓ Q2 — Where does "my profile" live, and who authors it?: The gap report is
  only as good as your profile data. Options: (a) hand-authored structured
  entities in Postgres, edited via API/UI; (b) upload your existing CV once, AI
  parses it into the structured profile; (c) a YAML file in the repo, no DB for
  profile. Note (b) sounds great but means your source of truth is AI-extracted
  and possibly wrong — you'd be comparing offers against a hallucinated version
  of yourself.

  ➡️ (a), with a one-shot JSON/YAML import endpoint to seed it. Profile is
  verified ground truth; never AI-written. (b) becomes a convenience importer
  later, always with human confirmation.

  ---
  ❓ Q3 — Can the AI write CV content, or only select from verified facts?: This
  is the trust boundary of the whole product. If the model freely generates
  bullet points tailored to an offer, it will eventually claim you used Kafka.
  Options: (a) strict — the AI only chooses which profile items to include,
  their order, and rephrases within a bounded rewrite (no new
  nouns/technologies); (b) free generation with a human review screen. (b) is
  more impressive in demos and is how you end up lying on a CV by accident.

  ➡️ (a) strict. Every technology on the rendered CV must trace to a profile
  record. Make it a testable invariant, not a prompt instruction.

  ---
  ❓ Q4 — CV rendering pipeline: You want a fixed, standardized template.
  Options: (a) Thymeleaf HTML → PDF via openhtmltopdf (pure JVM, no native
  binary, works on a 512 MB box); (b) Typst or LaTeX → PDF (beautiful, needs an
  external binary — awkward on free hosting); (c) DOCX via docx4j (many ATS
  parse DOCX best, but templating is painful). Worth knowing: some ATS still
  mangle multi-column PDFs, so single-column is the safe layout regardless.

  ➡️ (a) Thymeleaf → openhtmltopdf, single-column. Same HTML doubles as the
  browser preview in the Astro frontend later, so you build the template once.

  ❓ Q1 — How does matching actually work?: This decides whether your gap report
  is trustworthy or vibes. (a) Pure LLM — hand it the offer and your profile,
  ask for the gap. Simple, one call, but non-deterministic: the same offer gives
  different gaps on Tuesday, and you can't unit-test it. (b) Deterministic over
  a canonical catalog — you maintain a skill catalog with aliases (React ←
  ReactJS, React.js), the LLM's only job is extracting offer requirements and
  snapping them to catalog entries, then Kotlin does a plain set-diff. Testable,
  reproducible, but you curate a catalog. (c) Hybrid — (b) for the gap
  computation, plus one LLM call that turns the computed diff into readable
  narrative and the improvement plan.

  ➡️ (c) hybrid. The facts (what's missing) are deterministic and testable; the
  prose is generated. This is also the only version where "you have 7 of 10
  required skills" means the same thing twice.

  Round 3

  ❓ Q1 — How does a skill string become a canonical skill?: The hybrid diff
  only works if "container orchestration experience" and "K8s" both resolve to
  the same catalog entry. (a) Curated catalog + in-prompt snapping — you seed
  ~150–250 skills with aliases in a Flyway migration; the extractor receives the
  catalog and must return catalog IDs, emitting UNMATCHED for anything novel,
  which lands in a review queue you approve into the catalog. ~2k tokens per
  call, fully deterministic downstream. (b) pgvector embeddings — embed catalog
  entries and extracted strings, cosine-match above a threshold. Handles
  paraphrase without a big prompt, but adds an embedding model, a vector column,
  and a threshold to tune. (c) Alias map only, no semantic step — brittle,
  misses every paraphrase.

  ➡️ (a), with the review queue. The catalog grows organically from real offers
  instead of you guessing 200 skills upfront. Move to (b) only when the catalog
  outgrows the prompt — the review queue means you'll know when that happens.

  ---
  ❓ Q2 — Persistence stack: (a) Spring Data JDBC + Flyway — immutable Kotlin
  data classes, explicit aggregates (Offer owns its Requirements), no
  lazy-loading or session surprises, fast startup on a 512 MB box. (b)
  JPA/Hibernate + Flyway — the conventional Spring choice and probably what you
  know, but Kotlin needs the no-arg/allopen plugins, entities go mutable, and
  you inherit open-session-in-view foot-guns. (c) jOOQ — best SQL ergonomics,
  extra codegen step in the build.

  ➡️ (a) Spring Data JDBC + Flyway. Your aggregates are small and clearly
  bounded, and immutable Kotlin data classes map to it cleanly. Take (b) instead

  ---
  ❓ Q3 — Sync or async analysis?: An analysis is two LLM calls plus a Neon cold
  start — realistically 10–40s. (a) Sync POST /analyses returns the finished
  report. Simplest, but a 40s HTTP request will hit proxy timeouts on free
  hosting and gives the frontend nothing to show. (b) Async job — POST returns
  202 + jobId, GET /analyses/{id} polls PENDING → EXTRACTING → MATCHING → 
  DONE/FAILED. More code, survives timeouts, gives the Astro UI a real progress
  state, and makes retries sane. (c) SSE stream of tokens — nicest demo, most
  fiddly.

  ➡️ (b) async job with status polling. It's ~30 extra lines, and it's what
  makes the frontend and the free-tier deploy both work.

  ➡️ (a) single-user, no auth, localhost-bound, with a single static API key

  don't exist.

  ❓ Q2 — How are LLM calls structured?: (a) LangChain4j AiServices — one typed
  interface per task (OfferExtractor, ReportNarrator, CvTailor,

  @SystemMessage/@UserMessage backed by resource files so they're diffable. (b)
  Low-level ChatModel with hand-written prompts and Jackson parsing — more
  control, more boilerplate, no free schema enforcement.

  without seeing what the model actually returned. Caveat worth knowing now:
  strict JSON-schema support varies by underlying model on OpenRouter/Requesty,
  and most local models don't do it properly — so you need a retry-with-repair
  fallback, not just faith in the schema.

  ➡️ (a) AiServices + structured output + llm_call audit table + a parse-repair

⏺ Two corrections from the docs before the last round:

  - openhtmltopdf's original repo (com.openhtmltopdf, danfickle) has been 
  abandoned since ~2022. The live artifact is the community fork
  io.github.openhtmltopdf (https://github.com/openhtmltopdf) (v1.1.31,
  PDFBox 3). Use that groupId. The real constraint: it's CSS 2.1 only — no 
  flexbox, no grid. Your CV template will be tables and floats. Single-column
  ATS-safe layout is fine that way, but plan for it rather than discovering it.
  (Flying Saucer (https://en.wikipedia.org/wiki/Flying_Saucer_(library)) v10.0.6
  is the actively-maintained alternative and has the identical CSS 2.1 limit.)
  - Spring Modulith 2.0 GA requires Boot 4 — your 4.1.1 parent is exactly right,
  no version gymnastics.

  ❓ Q1 — What's the first thing you build?: (a) Walking skeleton — paste offer

  ➡️ (a) walking skeleton. It also means your stubbed test tier exists from day
  one instead of being retrofitted, which is where the CV invariant lives.

  ❓ Q2 — Which model handles which task by default?: Slightly
  counter-intuitive: (a) Everything via OpenRouter on a cheap capable model,
  with local Ollama as an opt-in profile you can flip per task. (b) Extraction 
  local, narrative remote — feels right (extraction is high-volume and
  mechanical) but extraction is precisely the task needing strict JSON schema,
  which is what small local models are worst at. (c) Everything local, remote as
  fallback.

  ➡️ (a). Put the hard structured-output work on a remote model where schema
  mode actually works, and treat local as the thing you experiment with once the
  parse-repair fallback is proven.

⏺ Plan written. Summary of what came out of the grilling:

  Three things changed materially from your original idea:
  - "Use LangChain" became LangChain4j, with the explicit understanding that
  you're learning the concepts, not the framework — the Python APIs won't
  transfer.
  - Your provider abstraction shrank from an SPI to ~40 lines of config, because
  OpenRouter, Requesty and Ollama are all the same wire protocol.
  - The gap computation became deterministic Kotlin over a curated catalog, with
  the LLM confined to extraction and prose — so "you match 7 of 10 must-haves"
  means the same thing twice.

  Four things were added that your spec didn't have: aggregate cross-offer gap
  analysis (the histogram is what should actually drive your learning plan, not
  any single offer), cover letters, offer lifecycle tracking, and a hard
  invariant test that fails the build if a technology appears on your CV that
  isn't in your profile.

  Two corrections from the docs you'd have hit later: com.openhtmltopdf is
  abandoned — use the io.github.openhtmltopdf fork, and accept CSS 2.1 (tables
  and floats, no flexbox). Boot 4 also ships Jackson 3, so imports are
  tools.jackson.*.

  Round 7 — CV rendering, revisited

  ❓ Q1 — How do you get a genuinely modern CV?

  (a) Playwright + headless Chromium. Thymeleaf → real Chromium print engine.
  You get everything: grid, flexbox, variable fonts, gradients, @page rules —
  and the PDF is pixel-identical to what the browser preview shows, because it
  is the browser. Cost is severe: a Chromium-bearing Docker image is ~2 GB and
  each render holds ~300 MB RAM. That definitively ends the Render-free-tier
  path and pushes you to Oracle Cloud or paid hosting.

  (b) Typst. A modern typesetting engine — a single ~30 MB static binary,
  renders in well under a second, negligible RAM. Output quality is better than
  HTML-to-PDF, not worse: this is a typesetting system, so kerning, baseline
  grids, and page breaks are handled properly. There's a mature CV-specific
  template ecosystem to start from (modern-cv
  (https://typst.app/universe/package/modern-cv/), clickworthy-resume
  (https://typst.app/universe/package/clickworthy-resume), impressive-impression
  (https://typst.app/universe/package/impressive-impression/)). Cost: it's
  Typst markup, not HTML, so you learn a small new syntax and you lose the "same
  template serves as the web preview" idea — the frontend would embed the
  generated PDF instead, which is actually higher fidelity.

  (c) Keep openhtmltopdf — ruled out by your requirement.

  ➡️ (b) Typst. It's the only option that satisfies both of your constraints — a
  genuinely modern-looking CV and a lightweight, free-hostable app. Chromium
  buys you HTML familiarity at the price of a 2 GB image and your hosting plan.
  And for a CV specifically, a typesetting engine is the right tool: those
  templates already look better than what you or I would hand-build in CSS.

  One knock-on if you pick (b): the Astro frontend previews the CV as an
  embedded PDF rather than rendering HTML, and generated_document stores the
  generated .typ source plus the selection JSON instead of HTML.

     Job Assistant — MVP Implementation Plan

     Context

     Fresh Spring Boot 4.1.1 + Kotlin 2.3.21 (Java 21) scaffold at
     com.jankowski.rafal.jobassistant.
     Only JobAssistantApplication.kt and a smoke test exist — no packages, no
     layering, no dependencies

     The problem being solved: job hunting is a repetitive manual comparison.
     For each offer you
     re-read the requirements, guess how well you match, and hand-edit a CV.

     skill_relation is how PARTIAL stays deterministic: you have a RELATED
     skill, not the exact one.
     - V3 offer — job_offer(content_hash UNIQUE, raw_text, title, company, 
     source_url, detected_language),
     application(offer_id, status, applied_at, notes).

     language, html, selection_json).

     ---
     Key mechanisms

     Match score — (metMustHaves + 0.5 × partialMustHaves) / totalMustHaves,
     with the formula shown
     in the report. Nice-to-haves reported but excluded from the score.

     The diff is deterministic. Given extracted requirements with canonical
     skill IDs and the profile's
     skill set: exact match → MET; skill_relation match → PARTIAL; neither →
     MISSING;
     canonical_skill_id IS NULL → surfaced separately and queued as an unmatched
     term. No LLM involved,
     so the same offer scores identically every time and it is all plain
     unit-testable Kotlin.

     AiServices interfaces (llm module, prompts in
     src/main/resources/prompts/*.md so they diff):
     - OfferExtractor → title, company, seniority, requirements (raw text +
     canonical skill ID +
     importance + rationale), detected language, red flags
     - ReportNarrator → summary markdown + learning plan items, from the
     already-computed diff
     - CvTailor → bullet IDs to include, their order, skill IDs to list, summary
     line, reworded bullet
     text keyed by bullet ID (so every output line traces to an input record)
     - CoverLetterWriter → same contract

     Parse-repair fallback — strict JSON schema support varies by model on
     OpenRouter and is mostly
     absent locally. On schema violation: one repair round-trip with the
     validation error, then fail the
     job with the raw response preserved in llm_call.

     The CV invariant test — tokenize the rendered Thymeleaf HTML text (not the
     PDF) and assert
     that every token matching a canonical_skill name or alias is present in the
     profile's skill set.
     Any skill on the CV that you don't have fails the build. Running against
     HTML keeps this in the fast
     CI tier with no browser needed — the single most valuable test in the
     codebase must never be slow
     enough to skip. A separate @Tag("pdf") test checks that Chromium actually
     produces a valid PDF.

     PDF rendering — a single long-lived Browser bean (launch costs ~1–2 s, so
     never per request),
     a fresh BrowserContext + Page per render, closed in a finally. A
     Semaphore(2) caps concurrent
     renders so memory stays bounded. page.pdf() with printBackground = true,
     A4, explicit margins;
     CSS @page rules control pagination. Fonts must be embedded locally or
     base64-inlined — no CDN
     references, so rendering stays deterministic and works offline.

     Async execution — @Async on a bounded ThreadPoolTaskExecutor; state lives
     in analysis.state
     so a restart can sweep orphaned RUNNING rows to FAILED at startup.
